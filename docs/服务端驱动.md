# 让客户端尽量不用更新

## 要解决的问题

iOS App 上架之后，改一个字、调一个排序、加一条提示，都要走一遍审核 ——
顺利也要一两天，被拒就是一周。而这套系统的**判断逻辑变得很快**：
今天发现「已表过态的要从待验收里扣掉」，明天发现「上游冻结的不算等你放行」。
这些都是服务端的认知在变，不该拖着客户端一起发版。

现状盘点（2026-08-16）：

- App 里 **53 处判断**（排序、健康度分级、新鲜度阈值）
- **384 处硬编码中文文案**

这两样每改一次都要发版，而它们绝大多数**本该由服务端决定**。

## 原则：App 是渲染器，不是计算器

| 谁做 | 什么 |
|---|---|
| **Mac 端** | 算什么该显示、怎么排序、显示什么文案、有哪些动作可选 |
| **App** | 把下发的结构画出来、把用户的选择写回去 |

App 不需要知道「什么是待验收」「怎么算浪费」，它只需要知道
「这是一个进度条区块，标题是 X，五条数据，第二条是警告色」。

## 具体形状

Mac 端往共享目录写 `views/<页面>.json`：

```jsonc
{
  "schema": 1,
  "page": "now",
  "generatedAt": "2026-08-16T14:00:00Z",
  "sections": [
    {
      "kind": "meters",              // 有限的几种，见下
      "title": "在漏的",
      "note": "按「已经连续空了几个窗口」排",
      "items": [
        { "label": "Codex · 5 小时", "fraction": 0.04,
          "tone": "warn", "right": "35 分钟后清零" }
      ]
    },
    {
      "kind": "cards",
      "title": "挡住了",
      "items": [
        { "title": "示例：素材包产线",
          "body": "方案等你过目 —— 批了才会在空窗时自动跑",
          "tone": "warn", "icon": "hand.raised",
          "actions": [
            { "id": "approve:demo-content", "label": "批准", "style": "primary" }
          ] }
      ]
    }
  ]
}
```

### 区块类型（`kind`）

这个集合**要小而稳定** —— 每加一种就是一次客户端更新，所以只加真正
无法用现有类型表达的。

| kind | 长什么样 | 覆盖 |
|---|---|---|
| `banner` | 一条带色的横幅，可带动作 | 提示、警告、演示模式 |
| `meters` | 一组进度条 + 左右标签 | 额度窗口、任何比例数据 |
| `cards` | 卡片列表，可展开，可带动作和图 | 待验收、待审批、任务 |
| `facts` | 键值对列表 | 统计、状态摘要 |
| `text` | 一段文字 | 说明、空状态 |

**不做任意 UI 下发。** 那需要一套布局语言，客户端要实现一个解释器，
维护成本高，而且 App Store 对「下发可执行内容」有明确限制。
语义化区块是数据，不是代码。

### 动作

App **不理解**「合入」是什么意思。它只知道：用户点了 `id` 为
`review:merge:/repo|branch` 的动作，于是往 `actions/` 写一个文件：

```json
{ "id": "review:merge:/repo|branch", "at": "...", "device": "iPhone" }
```

Mac 端的 work loop 认这个 id 前缀并执行。**加一种新动作不用动 App。**

### 未知的东西必须优雅降级

这是「以后能不能不更新客户端」的**前提条件**，比上面所有设计都重要：

- 未知的 `kind` → 跳过，不显示，不崩溃
- 未知的字段 → 忽略（`decodeIfPresent`，见 `SafeDecode`）
- 缺失的字段 → 用默认值，不是解码失败

只要这三条成立，服务端就可以先发新东西、客户端慢慢跟上。
反过来，任何一条不成立，服务端就被客户端的版本锁死了。

## 能力判断一律下发，客户端不许猜

这条是上面原则的一个特例，但它值得单列 —— 因为它出错的方式最隐蔽。

App 里曾经有这么一行：

```swift
var canEditFiles: Bool { platform != "minimax" }
```

写的时候是对的：MiniMax 那会儿只有一个纯文本执行器。后来它长出了
媒体和评审两个执行器，都写文件 —— 而这行代码停在原地。
结果是办公室里「点名让他干一件活」对它一直是灰的，点了没反应，
而它明明能干活。反方向也错：GLM 和 DeepSeek 根本没有执行器，
按这行判断却是「能派」，派了必然石沉大海。

**没有报错，没有崩溃，只是安静地说了三周谎话。**

现在改成服务端下发：

```swift
// Mac 端：问真实的执行器清单，不写平台名
r.canTakeWork = RunnerRegistry.all.contains { $0.platform == p && $0.canEdit }
```

```swift
// App 端：缺字段默认 true —— 老服务端没这个字段，
// 不能因此把按钮全锁死
var canEditFiles: Bool { canTakeWork }
```

两个要点：

1. **服务端也别写平台名**，去问真实存在的执行器。以后加一个执行器，
   这个判断自动就对了，不用记得回来改。
2. **不能派活时的原因也要下发。** 原来那句「他改不了文件」是写死的，
   等平台长出新能力，那句话本身就变成了谎话。

判断标准很简单：**这条判断的依据会不会在服务端变？** 会，就下发。
颜色和字体不会（它们跟着主题走），能力和状态会。

## 什么仍然留在客户端

这些改动频率低，留在 App 里是对的：

- 标签栏结构、导航
- 文件夹授权、安全作用域书签
- 图片加载与显示、手势、动画
- 演示模式（它必须在没有服务端时也能工作）

## 迁移怎么走

**不要一次全改。** App 已经在用，一次性重写等于把所有页面同时置于风险中。

1. **先做免疫**（最紧急）：让 App 对未知 kind / 未知字段 / 缺字段全部免疫。
   这一步不改任何现有页面的行为，但它是后面所有步骤的前提。
2. **新功能一律走视图层**：以后新加的东西直接下发，老页面不动。
3. **老页面逐个迁**：从改得最频繁的开始（「现在」页的判断和文案最多）。

每一步都能独立发版，任何一步出问题都不影响前面的。
