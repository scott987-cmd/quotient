# Agent 问答闭环修复 · 2026-09-03

状态：代码实现及本地验收；尚未安装到三台机器，也未发布配套 iOS 版本。不能据此声称线上 Agent 已产生新问答。

## 已复现的问题

1. `architecture-v1` 是任务终身唯一决策点；一旦旧答复被确认，新一轮真实失败不再触发咨询。
2. 协作投影先截 30 条事件，再截 12 张动作卡；原题和答复被新检查点挤掉，关系卡仅剩摘要。
3. iOS 只识别「问答」，服务端实际发「Agent 互问」；注册名录又被混进交流时间线与项目筛选。
4. 运行中读取协作上下文只返回最近 18 个事件；旧答复虽未确认也可能丢失。仅在初始上下文给咨询约定不够。
5. ack 允许部分采用或拒绝，界面却统一写成「已采纳」。

## 修复边界

- 保留旧 `architecture-v1` 关联。以真实失败 attempt ID 标识新决策点；已有未闭环咨询优先，不重复提问。
- 初次没有架构关键词时，至少两次执行/验证失败才要求咨询；旧咨询确认后出现新的执行/验证失败，再开一轮。额度、登录、会话失效不作为架构咨询触发条件。
- CLI `collaboration context --with-next-action` 保持 stdout 的事件 JSON 数组，附加动作写 stderr。MCP 保持第一文本块的数组，第二文本块给下一动作；不伪造或写入事件。
- 当前任务、项目、Owner 匹配才给运行期动作；问题、答复和反馈始终来自真实事件。
- 接收进程已经报告失败时明确给出阻塞提示，不继续无限等待、不把失败当答案、不自动换 Owner。
- 未确认的定向问答在上下文预算内保留原题与答案（最多 4 组、默认总数仍为 18）；确认后退出优先区，不无限重放旧全文。
- 看板按问题保留最近 8 组原题、最新有效答复和确认反馈全文。普通工作关系及最近 12 个动作独立展示。用户的「继续」和调度决定不计入 Agent 互问。
- 跨项目/任务的错误 replyTo 不能串成同一问答。兼容旧答复缺少接收者但显式引用原题的记录。
- iOS 独立展示「问题与答复 / 工作关系 / 最近动作」，名录默认折叠；兼容新旧统计字段；反馈标为「确认反馈」，采用与否以正文为准。
- 协作测试使用独立数据目录，避免测试发布投影污染真实看板。

## 不可夸大的部分

这是决定何时问、如何交付答复、如何展示的闭环，不是强迫模型制造交流次数。只有 Owner 实际提问、目标 Agent 实际作答、Owner 实际确认，账本才应出现这些事件。不补造历史问答，不冒充采纳，不为截图创建生产任务。

安装新版后，仍需观察一次真实任务的新故障 → 真实咨询 → 真实回答 → 采用/拒绝反馈。持续运行的旧进程不会自动加载新二进制，本轮没有中断 Flint 或更改 Owner，也没有发布客户端。

跨机咨询仍依赖发送者提供可读证据；本轮没有新增任意 SSH 执行或跨机仓库复制。模板明确要求传递分支/提交、失败证据和验收门槛，不应只发送接收方无法读取的本机路径。
