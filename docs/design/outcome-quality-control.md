# 设计：结果驱动的通用生产与质量控制

> 状态：阶段 0–1 已实现，2026-08-24；证据结构化及后续阶段待实现。
>
> 核心决策：**平台不再把“Agent 跑完、文件存在、测试通过”直接等同于成果完成。**
> 每个项目先把目标、约束、生产路线和验收证据编译成结构化执行契约；任务只能沿已准入
> 的路线推进，最终质量必须由与目标同维度的证据证明。

## 一、为什么现有机制仍然需要人盯每个点

现有系统已经解决了部分执行问题：

- `AGENTS.md` 保存稳定产品事实；
- `QUALITY.md` 会注入实现和评审任务；
- 可见改动必须交截图或录屏；
- 多模态 Agent 会做一次视觉复核；
- 项目负责人和项目会话保护执行上下文。

这些机制能减少“忘了要求”和“没有证据”，但还不能保证结果对：

1. **目标没有被编译成可判定的验收项。**“对标某产品”“要真实”“要高级”仍是文字，
   实现者和评审者可以各自解释。
2. **生产路线没有准入。**系统检查谁能接任务，却不检查“这条工具链是否有能力产出目标”。
3. **技术代理指标可以冒充最终质量。**文件存在、骨骼一致、单测通过、剪影不同都可能为真，
   最终画面仍然不合格。
4. **批量扩张没有黄金样板门。**第一件不对时，系统仍能连续生产八件同方向的错误成果。
5. **评审看到成果，却未必看到目标和参考物。**泛化地检查黑屏、穿模、T-pose，发现不了
   “结果和概念图根本不是同一个人物”。
6. **完成状态过于单一。**代码完成、技术可运行、体验达标、可发布被压成一个 `done`。

因此，问题不是再加一个更强的总管 Agent，而是把总管应遵守的判断变成系统状态和硬闸门。

## 二、目标与非目标

### 目标

1. 新项目只需在少数高杠杆节点由人确认，不需要人逐任务盯梢。
2. 在烧大量 token 之前发现目标与约束冲突、路线能力不足和错误的批量扩张。
3. 结构测试、行为测试、视觉体验和发布条件分层验收，低层通过不能冒充高层达标。
4. 执行者保持项目上下文，但不能私自降低目标或替换生产路线。
5. 被否决的原因沉淀为跨项目复用的失败模式，不在下一个项目重踩。
6. 移动端能看见任务处于哪一阶段、缺哪份证据、为什么暂停，而不是只看到“运行中”。

### 非目标

- 不试图用一套通用分数定义所有项目的“好”。通用内核负责流程和证据，游戏、App、媒体、
  后端等领域由质量 Profile 提供具体维度。
- 不让视觉模型替代最终产品判断。视觉模型负责高频拦截，人只保留黄金样板和版本级决策。
- 不要求每个任务换 Agent。实现仍遵循项目和能力泳道的上下文亲和。
- 不保证互相冲突的约束能被实现；系统必须尽早报告冲突，而不是偷偷降级结果。

## 三、通用模型：五份契约，一个状态机

### 3.1 Outcome Contract：最终要得到什么

每个项目登记：

- 产品的一句话核心结果；
- 用户能直接感知的成功条件；
- 明确非目标；
- 参考对象与只学习的原则；
- 原创、版权、安全、设备和发布时间边界；
- 预算、账号、外部服务、人工制作和许可证约束；
- 哪些条件允许协商，哪些是绝对约束。

现有 `AGENTS.md` 继续承载稳定事实；新增结构化索引只引用文件和条款 ID，不复制整篇文字。

### 3.2 Reference Contract：目标长什么样

凡是“像、对标、保持一致、达到某品质”的目标，都必须登记参考包：

```text
ReferenceItem
  id
  source / localFiles
  applicableDimensions
  learnPrinciples
  forbiddenCopying
  requiredViewsOrScenarios
```

参考不能只写产品名。必须落到可观察维度，例如角色轮廓、服装层次、面部可信度、动作重量、
输入反馈时间或信息层级。没有参考包时，涉及“相似度/品质”的任务不能进入最终质量阶段。

### 3.3 Production Route：准备怎样做出来

路线不是提示词，而是准入对象：

```text
ProductionRoute
  id
  deliverableKind
  sourceAssetsAndLicenses
  toolsAndServices
  requiredCapabilities
  expectedQualityCeiling
  deviceAndPerformanceBudget
  knownRisks
  validationStages
  fallbackRoute
```

路线准入必须回答：

1. 输入素材从哪里来，授权是否允许；
2. 哪个工具或角色完成每个生产步骤；
3. 该路线的质量上限是否覆盖 Outcome Contract；
4. 预算、账号、网络、设备和时限约束是否允许执行；
5. 在批量生产前，用什么黄金样板证明路线真实可行。

如果“零购买、无外部服务、无人手工建模”和“商业级原创 3D 角色”同时出现，系统应返回
`constraintConflict` 并列出需要放宽的约束，不能把程序化基础人体当作默认降级方案。

### 3.4 Acceptance Contract：怎样才算通过

验收条款必须带 ID，并分四层：

| 层 | 回答的问题 | 典型证据 |
|---|---|---|
| Integrity | 文件和结构真实吗、能加载吗 | 格式、授权、导入、骨骼、构建 |
| Behavior | 功能和规则正确吗 | 单测、集成测试、确定性回放 |
| Experience | 用户看到和感受到的结果对吗 | 参考对照、截图、录屏、实玩 |
| Release | 在目标环境可交付吗 | 实机性能、稳定性、安装与版本 |

每条标准包含：

```text
Criterion
  id
  layer
  description
  evidenceType
  evaluatorKind
  referenceIDs
  rejectConditions
  mutationOrNegativeCheck
```

硬规则：

- 低层通过不能覆盖高层缺失；
- “没有失败”不是“达到目标”；
- 代理指标只能证明它声明的维度；
- 最终质量条款必须使用与目标同维度的证据；
- 评审结论必须逐条引用 criterion ID。

### 3.5 Evidence Manifest：证据证明了哪一条

证据不再只是“分支里有一张 PNG”。每次交付生成清单：

```text
EvidenceItem
  file
  buildCommit
  deviceOrEnvironment
  scenario
  criterionIDs
  referenceIDs
  producedAt
```

系统检查的是“每条必需 criterion 是否有对应证据”，不是文件数量。引用参考的视觉条款必须把
参考物与实际结果以同角度、同场景或约定的对照方式交给评审者。

## 四、状态机：完成不再只有一个 done

项目交付状态统一为：

```text
draft
  → routePending
  → routeAdmitted
  → goldenSampleRunning
  → goldenSampleApproved
  → production
  → technicalReady
  → experienceReady
  → releaseReady
  → released
```

旁路状态：

```text
blocked.constraintConflict
blocked.missingCapability
blocked.missingReference
blocked.missingEvidence
rejected.quality
rejected.route
```

`WorkTask.done` 只代表一次执行结束，不能直接推进项目状态。推进由 Outcome Gate 根据验收票据决定。

## 五、自动闭环

### 5.1 立项编译

项目首次登记或目标发生实质变化时，架构/规划 Runner 将现有文档编译成五份契约。系统做静态检查：

- 必填目标是否为空；
- 参考对象是否只有名字、没有维度和证据；
- 约束是否冲突；
- 路线是否缺素材、许可证、工具或能力；
- 验收是否只覆盖 Integrity，没有 Experience；
- 是否定义黄金样板。

编译结果由人一次确认。确认的是“以后系统按什么判断”，不是每个实现细节。

### 5.2 路线准入

在普通任务分解之前先执行 `RouteAdmission`：

1. 根据 deliverable kind 找生产路线；
2. 用 Runner Registry 检查真实能力与工具；
3. 检查路线质量上限和项目目标；
4. 检查约束与许可证；
5. 不满足就阻塞并说明缺口，不派执行任务消耗 token。

Runner 能力不能只写 coding/media/review。需要登记可证明的交付能力，例如：

```text
swiftIntegration
visualReview
conceptImageGeneration
riggedAssetIntegration
threeDModelCreation
textureAuthoring
motionRetargeting
devicePlaytest
```

“能写 Blender Python”不自动等于“能制作商业级角色资产”。能力由成功交付记录和工具链共同证明，
不是由提示词宣称。

### 5.3 黄金样板门

任何批量内容先定义一个 Golden Sample：

- 一个角色，而不是先做八个角色；
- 一种僵尸，而不是先铺八种变形；
- 一张关键页面，而不是先迁完整 App；
- 一条真实数据链，而不是先铺所有接口。

黄金样板必须通过四层中适用的所有条款。未通过时：

- 同路线只能迭代样板；
- 禁止创建同类批量任务；
- 连续两次因同类根因未达标，自动回到 `routePending`，要求换路线而不是继续调参数；
- 人只在首次达标样板上做一次方向确认。

### 5.4 执行与上下文

- 同一生产路线和能力泳道保持 owner 与项目会话；
- 执行提示只注入当前阶段相关 criterion，避免整份合同反复烧 token；
- 执行者必须沿已准入路线工作；发现路线不可行时提交 `routeException`，不能私自降低目标；
- 跨能力交接通过资产、证据和结构化阶段产物，不通过重新复述整个项目；
- 长任务定期上报“当前阶段、已产物、下一验证、偏离路线与否”，供移动端和巡检使用。

### 5.5 独立验收

每类条款选择匹配的评审者：

- Integrity：确定性工具和测试；
- Behavior：测试 Runner；
- Experience：能读取全部参考物和证据的多模态 Reviewer；
- Release：目标设备验证与发布检查。

Experience Reviewer 的输入必须包含：目标条款、参考文件、实际文件、场景和拒绝条件。禁止只问
“画面有没有明显问题”。输出逐项为 `pass / fail / insufficientEvidence`，不能用一段自由文本猜状态。

实现者不能给自己的高层体验条款投最终票。独立评审失败时任务返回原 owner，保持上下文修正。

### 5.6 偏航巡检

`QualitySentinel` 在以下事件触发，不靠人定时盯：

- 黄金样板准备申请通过；
- 同类产物准备从 1 扩到 N；
- 连续完成若干任务但 Experience 分数/通过项没有改善；
- 同一个代理指标被反复用作完成证据；
- 路线、参考或质量契约发生变化；
- 版本准备发布。

巡检重点找模式，不重复普通代码审查：

- 数量增加，质量没有增加；
- 结构测试全绿，体验条款仍无证据；
- 实际成果与参考包身份不一致；
- Agent 为通过指标制造无意义差异；
- 仍使用已标为 graybox/placeholder 的资产；
- 任务标题持续写“完成”，项目状态却没有高层验收票据。

发现偏航后，系统冻结同类扩张、回退到最近一道真实通过的状态，并把整改派回原 owner或路线架构泳道。

## 六、人只保留三个高杠杆决策

默认只在人能提供独特价值时打扰：

1. **目标与约束确认**：产品到底要什么，愿意为哪些目标放宽预算、账号或周期。
2. **黄金样板确认**：方向是否正确，之后同类资产按已批准标准自动扩张。
3. **版本发布确认**：完整体验和商业判断。

其余审批只有在系统无法消解的真实冲突时出现。通知必须说明：冲突的两个条款、系统已尝试的路线、
可选择的放宽项和影响；不能只写“Agent 有个问题要你回答”。

## 七、移动端怎样展示

服务端下发语义状态，App 继续只渲染：

- 当前阶段：黄金样板 / 批量生产 / 体验验收 / 发布；
- 当前 owner 与最近一次真实进展；
- 已通过与未通过的验收层；
- 缺失证据和阻塞原因；
- 参考图与实际证据的对照入口；
- 需要人确认时，只显示上述三个高杠杆决策。

长任务的 UI 不能只显示“运行中”。如果一段时间没有新的阶段产物、验证或路线解释，标记为
“无可证明进展”，交给 `QualitySentinel` 判断偏航或继续等待，但不因单纯耗时自动换 Agent。

## 八、Flint 这次会怎样被自动拦住

如果这套机制已经存在：

1. Outcome Contract 写“写实商业角色品质，对标对象的角色层次和压迫感”；
2. Reference Contract 绑定人物概念图、僵尸概念图和指定视角；
3. MPFB 基础人体 + 程序化几何的路线申报质量上限；
4. RouteAdmission 发现它无法证明商业角色品质，且成熟路线被零预算、无账号等约束排除；
5. 项目在生产八种僵尸前进入 `blocked.constraintConflict`，要求只选择一次要放宽的约束；
6. 即使放行灰盒路线，也只能产一个标记为 graybox 的样板，不能进入 Experience Ready；
7. 视觉评审必须并排读取概念图和游戏图，裸人体换色无法通过人物身份、服装层次、材质和
   怪物形态条款；
8. 骨骼、PNG 和剪影测试只给 Integrity 投票，不能把项目标成美术完成。

这样人需要决定的只有“质量、预算、账号/服务、周期中放宽哪个”和“首个正式样板是否对”，
不需要亲自发现八个僵尸全是同一个裸模。

## 九、与现有系统的关系

保留并扩展，不另造重复调度器：

- `ProductBrief`：从注入整份 `QUALITY.md` 扩展为按阶段注入相关 criterion；
- `RepoExecutionPolicy`：继续负责项目 owner，新增生产路线/能力匹配前置准入；
- `EvidenceGate`：从“有没有证据文件”升级为 Evidence Manifest 覆盖率；
- `VisualQualityGate`：从自由文本结论升级为结构化 criterion 票据，并自动附参考物；
- `Milestone`：只展示已通过相应层级的成果，不能在独立质量票之前先落地再找人纠错；
- `TaskGraph`：按 Production Route 生成阶段节点，并由 Golden Sample Gate 限制批量 fan-out；
- 项目会话亲和：保持不变，整改返回原 owner；路线变更才进入架构泳道。

## 十、分阶段落地

### 阶段 0：先让缺口可见，不改变合入行为

- 增加项目契约结构、手写兼容解码和 `project doctor`；
- 把现有 `AGENTS.md`、`QUALITY.md`、`BENCHMARK.md` 编译成只读报告；
- 报告缺失参考、Experience 条款、路线和黄金样板；
- 用 Flint、移动端 App 和一个纯后端仓库做回放，校准误报。

已落地：

- `.llmq/project-contract.json` 的兼容数据模型与通用初始化命令；
- `llmq repo doctor <别名|路径> [--json]`；
- 目标、参考物、路线覆盖、硬约束冲突、四层验收和黄金样板的静态检查；
- 新游戏模板自动带契约骨架和 `PRODUCTION.md`；
- Flint 失败形状回放：程序化灰盒路线不能覆盖商业写实目标，成熟路线又全部触碰
  `deny:` 硬约束时，检查结果必须拒绝进入生产。

### 阶段 1：黄金样板和批量扩张门

- 为批量任务增加 deliverable kind、golden sample 和 fan-out 关系；
- 未通过样板时禁止同类扩张；
- 移动端显示阶段和阻塞原因；
- 先观察，不自动回退已存在项目。

已落地：

- `WorkTask.production` 保存交付物类型、黄金样板 ID、生产阶段和 fan-out 来源；缺少该字段的
  历史记录保持原行为，不被新闸门接管；
- `TaskIntake` 作为唯一入队入口，对照 `.llmq/project-contract.json` 验证生产关系；显式生产任务
  保持单任务/单会话，不被通用复杂任务拆解打断上下文；
- 黄金样板任务必须完成并合入主线；绑定 Experience 条款的样板还必须取得人工批准或
  `VisualQualityGate` 的达标票，同类 fan-out 才能派发；
- fan-out 可先登记，但会以准确原因保持 `blocked`；工作循环每轮重新对账，样板达标后自动
  重新排队，无需逐条人工重试；
- `TaskGraph.isReady` 在最终派发点再次核验样板，防止旧命令或手工状态修改绕过闸门；
- `llmq work add` 新增 `--deliverable-kind`、`--golden-sample`、`--fan-out-from`，并提供
  `llmq work approve-sample` 作为黄金样板人工确认入口；
- 服务端同时下发结构化生产字段和现有 `progress*` 兼容投影，不引入协议迁移；iOS“现在”页
  在没有运行任务时会把 blocked/queued 任务置顶，并直接显示阶段与 `progressNextStep` 阻塞原因。
  这项 UI 行为需要发布新版客户端；旧客户端只能看到“有任务卡住”的计数，不能看到完整原因；
- Flint 目前未放置生产契约，按“旧项目先观察”原则不会被倒退冻结；正式启用时必须先登记
  Flint 的真实参考、Experience 条款和首个样板，不能把已有八种产物倒填成已批准样板。

### 阶段 2：证据和评审结构化

- 引入 Evidence Manifest；
- Visual Quality Reviewer 必须读取参考包；
- 逐 criterion 保存票据；
- 变异验证：替换成明显错误参考、旧截图、同一资产换色，闸门必须变红。

### 阶段 3：路线准入和能力证明

- Runner Registry 扩充交付能力；
- 新项目和新 deliverable kind 强制 RouteAdmission；
- 约束冲突和能力缺失直接阻塞；
- 旧项目先告警，积累误报后再转硬闸。

### 阶段 4：偏航巡检和跨项目学习

- 上线 QualitySentinel；
- 把被否决原因归一为失败模式；
- 新项目编译契约时自动提示相关历史失败模式；
- 只学习规则和反例，不把旧项目内容、素材或具体实现复制到新项目。

## 十一、第一版验收标准

1. Flint 回放中，八种程序化僵尸扩张必须在黄金样板前被拒绝。
2. 只提供骨骼、PNG、构建和剪影证据时，Experience 状态必须保持未通过。
3. 视觉评审输入中必须同时出现适用参考和实际证据；缺任一项返回证据不足。
4. 修改或删除关键参考，`project doctor` 必须报错而非静默跳过。
5. 明显冲突的目标与约束必须在执行任务入队前被发现。
6. 同一黄金样板整改继续交给原 owner 和项目会话。
7. 用户不介入普通整改，仍能从不合格样板自动回到修正并再次评审。
8. 移动端能说明任务在哪个生产阶段、最近证明了什么、缺什么，而不是只显示持续时间。
9. 故意让结构测试通过但替换成错误视觉资产，最终质量门必须失败。
10. 通用内核能应用于游戏、App UI 和后端项目；领域差异只存在于 Quality Profile。

## 十二、架构原则

一句话概括：

> **让 Agent 对执行负责，让路线对能力上限负责，让证据对验收负责，让系统对持续偏航负责；
> 人只对目标、黄金样板和发布负责。**
