## 4. Codex 遗漏的已知病灶（应并入计划）

1. **retry 换人架空**：`work retry` 清 `triedPlatforms` 不清 owner（此前评审已确认的缺陷
   2.1）。属阶段 B 摄入/重试统一的一部分；不修，Ox 图盲那类死循环在新架构下照样复发。
2. **视觉整改回原 owner 无能力检查**：整改重投固定回「原 owner 原会话」，不查该 runner
   是否能处理图片载荷——这是 8-30 死循环的直接通路。P1-5 的能力模型只解决健康侧，
   整改重投路径要显式按 capability 路由。
3. **假搁浅告警**（1bf59288/11755fcb 误报链）在交接文档里有记录，本文未提，别丢。
4. **工作区基线混杂**：当前未提交改动混着 Codex 的调度/协作改动和我 8-25 冻结的止血件
   （`inFlightAgent` 工作区进程扫描加固、WorkspaceBusy 闸及其测试，已测绿未提交）。
   阶段 A 开工前必须先理清、分别处置，否则实现者接手的是脏底座。

## 5. 对原文 §8 八个问题的回答

1. **根因模型：写侧成立，但要并列第二根因。**「缺唯一状态转换内核」解释了事实漂移、
   晚到写入、镜像覆盖这一族。但 P0-2（nil 双义）、P1-5（platform vs runner 健康）、
   P1-6（name vs ID）、P2-2（两份点名分）是另一族病：**同一概念多处判定**。内核收敛
   治不了它，得靠「每个概念唯一判据 + 形状级回归测试」的纪律。两条根因都立规矩，
   否则内核修完这一族照样复发。
2. **是，构成阻断项。** 现场佐证：74726e09 单任务 rev 已写到 286——写入量足以把低概率
   短写变成必然事件；8-25 状态倒退事故已经演示过账本失真的代价。
3. **是。** nil 双义拆显式三态（focused / manualOnly / automaticAll）。
4. **是，附一条不可回退的约束。** 「有界摄入 → 冻结快照 → 唯一派发」正确，但摄入必须
   保持现有 watchdog 时限（20 秒级），不能让 iCloud 卡顿把派发重新拖停——首次派发提前
   正是为了治「老板一天问九次『又停了』」。顺序修正和延迟约束要同时写进验收门。
5. **方向同意，顺序有硬前置。** 必须先做 executor lease 持久化 + 「新协调器接管、不重复
   启动」的验收（原文 §7 已有此门），**验过之后**才允许放松 BinarySwap 闸。8-25 事故
   就是「接管未验证就换版」的形状。理清合入前，现役的 inFlightAgent 加固不能丢。
6. **选指定协调节点，且现成机制就在手边。** iCloud 无 CAS、mtime LWW、分钟级同步延迟，
   共享「真租约」在这个介质上做不出来。而 `ProjectExecutionScope` 已是本机状态、
   `shouldAutoRefill` 已要求 focus 命中——把「补活权 = 项目 focus 所在机」定为规则、
   配置上禁止两机同 focus 即可，与老板已定的「先不做跨机调度」一致。
7. **是。** 且要一并改三处：伪造 claim（改成接收方真实认领后才有 claim 事件）、
   result 自动关问题（改判据设计）、咨询适配器扩到 kimi/qwen 或在发现接口明确降级。
8. **两处顺序风险，一处保留项。**
   - 阶段 A 内部必须 2（transition 唯一入口）先于 3（清 32 处 `try?`）：调用方没有
     失败处置路径就清，等于把静默换成崩溃、或把静默搬进日志。逐调用点定处置
     （重试 / 转可见失败 / 排队），不能机械替换。
   - 阶段 B 入口统一要把「画像由付费方带来」「手机任务必分诊」这类刻意差异保留为
     intake 参数，不能一刀切抹平。
   - 阶段 C 见问题 5 的前置。其余未见会造成二次迁移的依赖错误。
