## 二、新发现：一个对阶段 3 的硬冲击

修订版 7.2 表格里两条关键默认动作：

- 首次超时且有修改/提交 → 原 owner 续一次
- 首次超时且零产出 → 原 owner fresh 重试一次

阶段 3 同时「取消超时后同一轮立即遍历剩余平台」。

**历史数据不支持这个方向。**23 个超时任务里最终成功的 12 条，逐条看是谁救活的：

```
0b3e3f20s3  超时于 kimi     → codex    换人才成功
2db95188    超时于 volcark  → kimi     换人才成功
69ab923e    超时于 volcark  → minimax  换人才成功
7dfed868s8  超时于 qwen     → kimi     换人才成功
83d68ae6    超时于 claude/qwen → volcark 换人才成功
a90f8b8cs5  超时于 kimi     → codex    换人才成功
be460b11s3  超时于 volcark  → codex    换人才成功
bf5791e2    超时于 volcark  → minimax  换人才成功
c06a02da    超时于 volcark  → codex    换人才成功
e048033c    超时于 qwen     → volcark  换人才成功
f4f65db2    超时于 kimi     → volcark  换人才成功
fac6b275    超时于 volcark  → kimi     换人才成功

原地重试成功 0 条    换人才成功 12 条
```

**必须同时说明这个数的局限（否则它会被过度使用）**：现有策略是「超时即换人」，
系统**从来没有在超时后重试过同一个平台**，所以「0 条原地重试成功」是策略造成的，
不是「原地重试无效」的证据。这是典型的选择效应，观测不到反事实。

但它仍然改变了风险判断：**阶段 3 要用一个 0 次观测的机制，去替换一个 12/12 观测成功的机制。**
这不是「取消一个几乎不触发的路径」（我一轮 review 说它 1/517 触发，那个判断基于错误的超时统计，
一并撤回），而是动一条真实在救火的路径。

**建议**（不反对方向，反对无度量地切换）：

1. 阶段 3 拆成 3a / 3b。3a 只做「已有 owner 的任务不再全平台重排」，
   **保留超时后的换人兜底**；3b 才引入「原 owner 先重试一次」。
2. 3b 必须是可度量、可回滚的：把「原 owner 重试成功率」和历史「换人成功率 12/12」
   放在同一张表里比。低于历史值就回滚，而不是靠论证。
3. 顺序上建议：**先做超时预算校准，再做 3b**。理由见下一节。

## 三、超时高度集中在特定平台——很可能根本不是调度问题

按平台统计超时率（超时日志数 / 该平台总运行日志数，含归档）：

```
volcark   12 / 83  = 14%
qwen       4 / 29  = 13%
kimi       7 / 98  =  7%
claude     2 / 59  =  3%
```

火山和 Qwen 的超时率是 Claude 的 4–5 倍。结合待修清单第 3 条
（复杂档 45 分钟对 FPS 级编码任务太紧，`c3dcbbaa` 干到 95% 被砍），
**相当一部分超时是时限设错，不是 Agent 卡死，也不是调度策略的问题**。

建议把「按平台/按难度校准超时预算」作为**阶段 0 的一部分**（它只改配置和统计，
不碰调度），先把这一层噪声去掉。否则阶段 3 的「原 owner 续一次」会让同一个 Agent
在同一堵墙上撞两次，而墙是时限本身。

## 四、修订版设计里我认为要显式写明的两个后果

### 4.1 会话作用域改成 task 之后，普通任务实际上不再复用会话

5.2 定义普通任务 session key = `taskID + runnerID + machineID`。
普通任务在正常路径下只跑一次，因此**每条新任务都是 fresh session**——
「省去重读仓库」这个收益对普通任务**完全消失**，只在同一任务的重试/恢复路径上还存在。

这是对的（仓库级知识本来就该由 `AGENTS.md`/RepoMap/STATUS 承载，5.2 也这么写了），
但要预料到一个可观测的副作用：**改完之后普通任务的 token 消耗大概率上升**。
建议在阶段 1 的验收里直接写上「预期 token/任务上升，不视为回归」，
免得上线后被当成 bug 回滚——这个项目踩过的形状是「修好了到不了眼前」，
这里的风险是反过来：「改对了却被误判成改坏了」。

### 4.2 人工停用消耗掉唯一一次自动交接

7.3 决定人工停用的交接计入 `handoffCount`，7.5 又规定「一条任务最多自动交接一次」。
两条合起来：**老板静音一个平台，就会把该 owner 名下任务的自动交接名额用掉**，
之后遇到真实故障必须人工授权。

今晚就有这个场景（Codex 被静音）。我不反对这个取舍（`handoffCount` 统计上下文转移次数，
语义是自洽的），但建议在 7.5 里显式写一句：**人工停用导致的交接不计入自动交接上限**，
或者至少在任务记录里区分这两种 handoff 来源——否则「为什么这条任务不肯自动接力了」
会变成又一个查不出来的黑盒。

## 五、对修订版的总体结论

阶段 0 → 1 → 2 → 3 → 4 这个新顺序我完全同意，它比我一轮建议的顺序更好：
增加 WorkAttempt 放在最前面是关键一步——**我们两个人这一轮都在同一个地方栽跟头
（最终记录抹平了中间尝试），这正是 WorkAttempt 要解决的东西。**

需要修改的只有一处：**阶段 3 拆成 3a/3b，3b 前置「超时预算校准」并且必须可回滚**。

其余（能力泳道 owner、session 作用域收紧、`projectLatest` 的 affinity 校验、
永久不可用的分级判断、日志措辞）我没有异议，其中几条比我一轮的建议更准确：
未知 runnerID 不猜平台、`projectLatest` 只禁同 cwd 并发、探针不作为统一前置动作——
这三条修订版都比我说得对。
