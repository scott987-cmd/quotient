# 项目级会话亲和

> 2026-08-24，阶段 3b 决策。本文覆盖 `context-affinity-scheduling.md` 中“普通新任务必须新建会话”的旧结论。

## 决策

原生会话的作用域统一为：

```text
机器 × Runner × 稳定工作区 × 能力泳道
```

稳定工作区已经按“仓库 × Agent”隔离。同一个 Agent 在同一项目接到下一条任务时，继续自己的项目会话；不同 Agent、不同项目、编码/媒体/评审泳道之间不共享会话。

`taskID` 继续用于任务归属、尝试记录和交接审计，但不再作为切断项目上下文的边界。

## 原因

任务级会话避免了串任务，却让同一个项目的连续工作反复从零开始。仓库地图和 STATUS 能恢复事实，不能恢复模型刚形成的实现理解、失败路径和局部设计判断。稳定工作区已经提供了更合适的隔离边界，继续按 taskID 新建会话是在重复隔离。

会话不是唯一事实源。需要跨 Agent 或长期保存的结论仍必须落到 `AGENTS.md`、`STATUS.md`、代码、测试和证据中；项目会话只负责减少同一 Agent 的重复理解成本。

## 执行器能力

| Runner | 恢复方式 | 调度语义 |
|---|---|---|
| Claude | 显式 session ID | 首次创建，后续精确恢复 |
| ZCode | 从真实输出取得 session ID | 取得后精确恢复 |
| Qwen | `-c` | 恢复稳定工作区最近会话 |
| Kimi | `-c` | 恢复稳定工作区最近会话 |
| Codex | `exec resume --last` | 恢复当前工作区最近会话 |
| OpenCode | `run -c` | 恢复稳定工作区最近会话 |
| Gemini | `--resume latest` | 恢复当前项目最近会话；当前未进生产 Runner 列表 |
| MiniMax 媒体/评审驱动 | 无原生会话 | 依赖稳定工作区和磁盘材料，不伪装成已恢复 |

## 保护规则

1. 只有同一机器、同一 Runner、同一稳定工作区、同一能力泳道才能恢复。
2. `--last` / `-c` 只在该工作区已建立项目亲和标记后使用；首次运行保持 fresh。
3. 旧 `repo:<path>|<platform>` 项目标记升级时迁移到稳定工作区。精确 ID 原样迁移；project-latest 型只迁移“存在历史”这一事实，不把旧 UUID 冒充 CLI 会话 ID。
4. 只有明确的 session/conversation 失效错误才能清理会话；普通构建失败和超时保留上下文。
5. 清理只影响一个 Agent 在一个项目/泳道的会话，不波及其他项目。
6. Agent 不可用或能力不匹配时允许交接，但必须保存 WIP、触碰文件、失败原因和证据；不得为了均摊额度无理由换人。

## 验收

- 同一 Agent、同一稳定工作区、不同 taskID：恢复同一项目会话。
- 同一 Agent、不同工作区：创建不同会话。
- 同一工作区、不同 Runner 或能力泳道：会话隔离。
- Kimi/Qwen/OpenCode 首次不带 `-c`，恢复时才带。
- Codex 首次走 `exec`，恢复时走 `exec resume --last`。
- 旧仓库级亲和标记能启动新稳定工作区的首次恢复。
- 会话失效只清理精确的项目/Runner/泳道映射。
