# 设计：上下文连续性优先的多 Agent 调度

> 状态：提案，等待 Claude review；本文档没有授权实现或发布。
>
> 决策摘要：**额度只决定一条新任务第一次交给谁，不应决定已经开工的任务下一轮换给谁。**
> 任务一旦开始，默认绑定同一台机器、同一个执行器、同一个原生会话和同一个工作区；
> 跨 Agent 接力是故障降级，不是日常负载均衡。

## 一、为什么要改

当前调度器在首次派发时会生成按额度、角色偏好和仓库粘性排序的候选列表，
随后在同一次 `runOneTask` 里依次尝试。平台不可用或超时时，会立刻换下一个平台。

这保护了任务不因某个平台故障而完全停住，但把两件不同的事混在了一起：

1. **新任务分配**：谁最适合从零开始。
2. **已开工任务恢复**：谁拥有这条任务已经形成的上下文。

对第一件事，额度、能力和可用性都应该参与选择；对第二件事，最重要的是上下文连续性。
换平台后，即使保留了 worktree、WIP commit 和文件清单，仍会丢掉：

- 为什么选择当前实现而不是另一个方案；
- 已经读过哪些代码、排除过哪些路径；
- 哪些尝试失败过以及失败原因；
- 模型在原生会话中形成的项目理解和隐含假设。

这些信息无法靠一段 handoff 文本无损重建。新 Agent 重新探索仓库消耗 token，
还可能推翻前一位已经验证过的判断。因此，“谁额度多谁接下一棒”可能让看板更忙，
但不一定增加有效产出。

### 当前实现里的直接证据

- 仓库粘性只是 `0.12` 的软加分，额度差距更大时仍会换人：
  `Sources/LLMQuotaCore/Work.swift` 的 `stickinessBonus`。
- `FailureKind.timedOut` 和 `platformUnavailable` 都会触发 `shouldTryNextPlatform`，
  `runOneTask` 会继续遍历候选列表。
- `GraphSession.Mode` 在协议层有默认“忽略 session”的实现；目前只有少数 Runner
  真正覆盖了恢复命令，但主循环会对所有 Runner 打印“接上会话”。
- `triedPlatforms` 记录“试过谁”，但没有记录“这条任务的负责人是谁”。

## 二、设计目标

1. 普通任务从开工到完成，默认由同一个 Agent 闭环。
2. worker 重启、进程超时、会话失效时，优先恢复原负责人，而不是立刻换平台。
3. 只有明确的永久故障或能力不匹配才允许交接。
4. 继续保留独立 worktree、WIP commit、风险闸、额度留白和人工使用避让。
5. 多 Agent 的价值来自**独立任务并行和专业能力分工**，不是同一任务频繁换手。
6. 日志和看板只报告真实发生的会话恢复，不把“传了一个随后被忽略的参数”说成续上会话。

## 三、非目标

- 本轮不做跨机自动调度。`Docs/design/cross-machine-routing.md` 已明确标记为搁置，
  产物回传问题没有解决前不得顺手接入。
- 不追求“所有 Agent 始终繁忙”。没有独立真需求时闲置，优于制造重复探索和无价值产出。
- 不把同一仓库拆成文件级并行写入。派活前无法可靠预测 Agent 会碰哪些文件。
- 不为了这项改造重写整个任务状态机或额度引擎。
- 不假设所有 CLI 都支持原生会话恢复；不支持就是不支持，必须如实表达。

## 四、核心不变量

### 4.1 任务负责人

一条任务第一次真正开跑前选出 `owner`：

```text
TaskOwner = 本机 + runnerID + platform
```

本轮不需要把“机器”写入跨机协议：任务库本来就是本机私有的；记录 `runnerID` 是因为
同一个平台可能有多个执行器，例如 MiniMax 的媒体执行器和评审执行器不是一回事。

负责人一旦落盘，后续调度遵守：

```text
owner 仍能完成任务 → 只恢复 owner
owner 暂时不能执行 → 等待或恢复，不换人
owner 永久不可用/能力不匹配 → 才评估交接
```

### 4.2 额度的职责边界

额度参与**首次选人**，不参与**中途换人**。

- 新任务：可以按能力、风险、额度留白、人工使用、历史成绩选负责人。
- 已开工：即使另一个平台剩余更多，也不能仅凭这一点抢走任务。
- 负责人额度暂时耗尽：保留任务、工作区和会话，等重置。
- 用户明确指定截止时间或手动要求换人：才允许覆盖默认策略。

### 4.3 并发的边界

允许：

- 不同仓库的独立任务由不同 Agent 同时执行；
- 同一仓库中已经证明互不依赖、且不共享写入基线的只读任务；
- 媒体生成、独立评审等以文件产物为边界的专业任务。

不允许：

- 同一任务的两个步骤为了吃额度而由不同编码 Agent 并行修改；
- 同一个共享 worktree 中并行写入；
- 因为某个平台剩余比例更高，就接管已经开工的任务。

并发是后续优化，必须排在任务负责人绑定和真实会话恢复之后。

## 五、调度流程

### 5.1 新任务：只在这里做全候选排序

1. 按现有硬闸过滤：任务类型、视觉能力、风险、复杂度、Runner 可用性、冷却、静音、留白。
2. 在剩余候选中排序，选出一个负责人。
3. 在启动子进程之前原子落盘 `ownerPlatform` 和 `ownerRunnerID`。
4. 创建或取得这个负责人在该仓库上的原生会话。
5. 后续重试不再重新运行全候选排名。

首次排序仍可以优化，但不属于本提案的前置条件。即使排序暂时不完美，
“选定之后不随意换人”也能独立减少上下文浪费。

### 5.2 恢复：先回原负责人

恢复顺序固定为：

1. 原 Runner + 原生 session + 原 worktree；
2. 原 Runner + 新 session + 原 worktree（仅会话已损坏时）；
3. 原 Runner + 新 session + RepoMap/ProductBrief/WIP briefing；
4. 经确认可以交接后，才选择另一个 Runner。

这里的“原 Runner”必须精确到执行器，不只是平台。MiniMax 媒体任务不能恢复到
MiniMax 评审执行器，反过来也不行。

### 5.3 失败怎么处理

| 情况 | 默认动作 | 是否换 Agent |
|---|---|---|
| worker 重启、进程被系统打断 | 原负责人恢复原会话和 worktree | 否 |
| 首次超时但已有进度 | 保存 WIP，原负责人续一次；下一轮给更合理的时限 | 否 |
| 首次超时且零产出 | 原负责人重新开一次；再次超时才转人工判断是否交接 | 默认否 |
| session 不存在、过期、已占用 | 丢掉 session 映射，原负责人新会话继续 | 否 |
| 临时额度耗尽且有重置时间 | 保持 queued/paused，等重置 | 否 |
| 登录失效、CLI 被卸载、端点长期不可达 | 保存进度并生成明确交接原因 | 可以 |
| 派发前发现能力不匹配 | 重新选负责人；此时尚未形成上下文 | 可以 |
| Agent 真执行了但实现/验证失败 | 原负责人修复，或转独立评审；不盲目重做 | 默认否 |
| 用户明确要求换人 | 保存交接包并重新选负责人 | 可以 |

“超时”等于“应该马上换人”的现有假设需要取消。超时可能说明任务比估时更大，
也可能说明 Agent 正在完成长验证；换人会让下一位重复同样的探索。

### 5.4 允许交接时

交接仍然是降级路径，必须保留下列事实：

- 原负责人和原 Runner；
- 中断原因以及它是临时还是永久；
- worktree、分支、WIP commit；
- 已修改文件、已运行验证和验证结果；
- 尚未完成的明确事项；
- 交接次数。

一条任务默认最多自动交接一次。第二次仍失败时停止自动轮转，避免三个平台依次重读仓库。

## 六、任务图与专业 Agent

任务图不能天然等同于“每个节点换一个 Agent”。默认规则是：

1. 后续节点能力要求与上一步相同，则继承负责人并恢复同一会话。
2. 只有能力边界不同才换专业执行器，例如：
   `MiniMax 生成资产 → Kimi 接入代码 → MiniMax 看效果`。
3. 专业步骤通过明确文件产物交接，不依赖另一家模型理解上一家的隐藏思考。
4. 专业步骤结束后回到原编码负责人时，恢复原编码会话，而不是重新选“当前额度最多”的编码 Agent。
5. 共享 worktree 的图继续串行执行，本提案不改变这一点。

这要求任务类型最终从提示词前缀升级为结构化字段；但第一阶段可以保留现有
`TaskKind`，先把 owner 绑定做实，避免扩大改动面。

## 七、最小数据改动

为了让兼容风险可控，第一阶段只建议给 `WorkTask` 增加：

```text
ownerPlatform: Platform?
ownerRunnerID: String?
ownerAssignedAt: Date?
handoffCount: Int
```

给 `AgentRunner` 增加两个真实能力：

```text
runnerID: String
sessionSupport: none | projectLatest | stableID
```

要求：

- 新字段全部手写 `decodeIfPresent`，旧任务按“尚未分配负责人”处理。
- `platform` 继续表示当前/最终实际执行者，不偷换现有字段语义。
- `ownerPlatform` 表示任务负责人；发生合法交接时显式更新，并增加 `handoffCount`。
- `sessionSupport == none` 时不得创建伪 session 记录，也不得打印“接上会话”。
- 不新增一套和 `GraphSession` 平行的 session 存储，扩展现有实现即可。

## 八、落地顺序

### 阶段 1：负责人绑定

- 首次选人后落盘 owner。
- 已有 owner 的任务只构造 owner 候选，不做全平台重新排名。
- 取消“超时后在同一轮立即遍历剩余平台”的默认行为。

验收：一个可恢复的超时任务，下一轮仍由同一 Runner 执行。

### 阶段 2：会话能力说真话

- 给每个 Runner 声明 `sessionSupport`。
- 只有真实支持的 Runner 才调用 create/resume。
- 修正普通任务恢复失败时忘错 session key 的路径。

验收：支持恢复的 CLI 能在第二次执行中回答只存在于第一次会话的信息；
不支持的 CLI 日志明确显示“沿用工作区，Runner 不支持原生会话恢复”。

### 阶段 3：任务图继承 owner

- 同能力节点继承 owner。
- 跨能力节点单独选专业执行器。
- 返回原能力时恢复原 owner 的 session。

验收：一张“生成图片 → 接入代码”的图只在能力边界换人，多个编码步骤不换人。

### 阶段 4：独立任务并发（可选，最后做）

只有前三阶段真实运行稳定后，才评估每机 2 个执行槽。必须继续满足：

- 一个 Agent 同时只做一个任务；
- 一个仓库同时只有一个写入任务；
- 每个任务内部保持 owner 和 session；
- 全局速率、留白和人工使用避让仍然生效。

## 九、验证标准

### 单元测试

1. 新任务只选一次 owner；额度数据变化不能改变已开工任务的 owner。
2. owner 暂时冷却时任务等待，不进入其他平台候选。
3. worker 中断后清除“失败过”标记，但保留 owner。
4. session 失效后仍由原 owner 新开会话。
5. 只有永久不可用或显式授权能增加 `handoffCount`。
6. `sessionSupport == none` 时不会产生 session 映射和虚假恢复日志。
7. 旧 JSON 不带新字段仍可读取。
8. 图内同能力节点继承 owner，跨能力节点才允许不同 Runner。

按照 `docs/no-faking.md`，关键测试需要做变异验证：临时恢复旧的“超时就换下一个平台”逻辑，
确认 owner 连续性测试真实变红，再恢复实现。

### 真机验证

1. 给支持会话恢复的 Agent 第一轮一个随机事实，让任务被人工中断；第二轮不重复提供，
   要求它从原会话准确复述并继续工作。
2. 构造一次短超时，确认同一 Runner、同一 worktree、同一 session 恢复。
3. 构造一次登录失效，确认保存 WIP 后只交接一次，并在任务记录中说明永久原因。
4. 构造一张跨媒体/编码能力的图，确认只在产物边界换 Agent。
5. 手机任务板要能区分“等待原负责人恢复”和“已交接给另一位”。

### 观察指标

- 单任务平台数：普通任务目标值为 1。
- 自动交接率：应接近 0；上升必须能按失败类型解释。
- 同 owner 恢复成功率。
- 原生 session 真正命中的次数，按 Runner 分开统计。
- 完成、验证通过、最终落地三个口径必须分开。
- 每个落地任务的 headless token；没有任务级归因前，不宣称“省了多少 token”。

## 十、需要 Claude 重点 review 的问题

1. “临时额度耗尽就等待原 owner”是否可能造成不可接受的队头阻塞；现有跳过队头机制能否完整兜底？
2. 超时后原 owner 应自动重试几次，怎样区分“任务确实更大”和“Agent 已经卡死”？
3. `ownerRunnerID` 是否足够稳定，发布升级后 Runner 改名时如何兼容？
4. Qwen 的 `projectLatest` 与 Claude/ZCode 的 `stableID` 是否应该共用一个枚举，还是会掩盖关键语义差异？
5. 普通任务和任务图当前使用不同 session key；统一 owner 后是否存在错误串会话的风险？
6. 高危任务由指挥兼任时，owner 绑定是否会占住控制面；是否必须设置单独的人工确认或控制面预算？
7. 哪些失败可以被可靠判成“永久不可用”，避免把一次误分类变成不必要的跨 Agent 交接？
8. 阶段 1 能否在不引入新状态枚举的情况下完成，保持改动足够小？

## 十一、最终原则

这套系统优化的目标不是“把所有订阅的进度条都烧完”，而是：

> 在真实需求范围内，让最合适的 Agent 持续拥有任务上下文，
> 用尽可能少的重复探索获得可验证、可落地的结果。

额度是资源约束，不能凌驾于任务上下文；多 Agent 是产能池，不能变成同一任务的轮流重读器。

## A.2 关键数据：问题的真实规模——**优先级应该倒过来**

提案的阶段 1（任务中途不换人）和阶段 3（任务图继承 owner）解决的**不是同一量级的问题**。

**任务中途换平台：517 条里只有 18 条（3.5%）**

```
试过 1 个平台   393 条 (76%)
试过 2 个平台    14 条 (2%)
试过 3 个平台     3 条
试过 4 个平台     1 条
```

这 18 条里，**被换掉的那位有 9 条根本没真开工**（日志 < 2KB 或压根没有日志文件，
即 `platformUnavailable` 在启动前就淘汰了它）——这 9 条是故障转移**正常工作**，不是浪费。
真正「已经干出上下文却被换掉」的只有 **9 条**。而且 18 条换人任务里 **16 条最终 done**，
换人后仍失败的只有 2 条。

**超时换人这条路几乎不触发**：全库带超时痕迹的 9 条，**最终全部 failed**，其中只有 1 条换过平台。
说明现实里超时任务不是「被换给下一位」，而是耗尽候选后直接失败。
所以阶段 1 里「取消超时后立即遍历剩余平台」这一项，改的是一条约 1/517 触发的路径。

**任务图相邻步骤换人：117 对里 54 对是「同能力却换了人」（46%）**

```
同能力·不换人   53 (45%)
同能力·换了人   54 (46%)   ← 上下文真正被大量扔掉的地方
跨能力·不换人    6 (5%)
跨能力·换了人    4 (3%)    ← 能力边界，该换，提案也认可
```

（能力按「编码/评审/媒体」分。注：先按 `profile` 分过一次是错的——那是难度不是能力，已重算。）

样例：图 `aec624dc` 连续四个编码步骤走了 `volcark → claude → kimi → qwen`；
图 `7dfed868`、`a90f8b8c` 同样每步换人。这些步骤共享同一个 worktree、同一条分支，
每换一次就得重读一遍仓库。

**结论：建议把提案的阶段 3 提到阶段 1。**
按数据，「任务图同能力步骤继承 owner」覆盖 54 例，「任务中途不换人」覆盖 9 例，
而后者里还有一半是故障转移的正常行为。当前排序会先花力气改动最敏感的主调度路径
（`runOneTask` 的候选遍历），换来的收益却最小。

## A.3 提案低估的一条：「接上会话」这句话 **87% 是假的**

提案说「主循环会对所有 Runner 打印『接上会话』」。实测下来更严重：

- `Work.swift` 里只有 **ClaudeRunner**（`--session-id` / `--resume`）、**QwenRunner**（`-c`）、
  **ZcodeRunner**（`--resume`）有 session 分支；
- **KimiRunner / CodexRunner / OpenCodeRunner(火山) / MiniMaxRunner 各有 0 处 resume 分支**——
  传进去的 `GraphSession.Mode` 被静默丢弃；
- 而 `main.swift:2219` 只要映射表里有 id 就打印「接上会话 xxxxxxxx（省去重读仓库）」，
  不看 Runner 认不认。

按任务库回放「第二次及以后在同一 (图/仓库 × 平台) 上跑」的次数：

```
真的接上了      41 次
纯属谎话       283 次   ← kimi/codex/volcark/minimax
说谎占比        87%
```

这正是 `docs/no-faking.md` 要防的形状，而且它**污染了所有关于上下文的判断**——
包括这份提案的立论基础：我们以为「换平台才丢上下文」，实际是**不换平台也在丢**，
Kimi 在同一个仓库连着跑 20 次，每次都是从零重读，而日志 20 次都说「省去重读仓库」。

**建议：阶段 2 提到最前面。**它改动面最小（给 Runner 加一个 `sessionSupport` 声明 + 打印前判一次），
却是唯一能让后续所有度量（第九节的「原生 session 真正命中次数」）说真话的前提。
在它落地之前，任何「上下文连续性提升了多少」的结论都不可信。

## A.4 一个方向性隐患：现在的会话粒度是「仓库级」，不是「任务级」

`GraphSession.mode(repo:platform:graphID:)`（`GraphSession.swift:124`）：

```
图内任务：  key = graphID + "|" + platform
普通任务：  key = "repo:" + 仓库绝对路径 + "|" + platform
```

普通任务的 key **不含任务 id**——意味着**同一仓库、同一平台的所有任务共用一个会话**。
两条毫无关系的任务（比如「修 fd 泄漏」和「改发布脚本」）会接进同一段对话历史。

这和提案的方向是**反的**：提案想增加「同一条任务」的连续性，
而现状是「同一条任务」的连续性缺失（图内 46% 换人）、
「不相关任务之间」的连续性过度（共用会话）。

如果只做 owner 绑定而不动这个 key，会把「不相关任务串在一起」这件事绑得更死。
**建议在阶段 1 或 2 里一并决定会话粒度**：至少让普通任务的 key 带上任务 id 或 graphID，
让「一条任务一段会话」成立。第十节问题 5 问的「统一 owner 后是否存在错误串会话的风险」——
答案是：**风险现在就已经存在，不是统一 owner 之后才有的。**

## A.5 提案没覆盖的交互：静音 / 不接活 × owner 绑定

第 4.1 节写「owner 暂时不能执行 → 等待或恢复，不换人」，但没定义**静音**算哪一种。

现实例子（就在今晚）：老板要求「不要给 Codex 安排工作了」，我执行了
`llmq runner roles --set codex --mute-here`，`roles.json` 现在是：

```json
{"platform":"codex","mutedOn":["杜师兵的Mac mini"],"canTakeWork":true}
```

静音**不是**额度耗尽那种「等一会儿就好」，也**不是**「登录失效」那种永久故障——
它是人主动设的、没有恢复时间的状态。按提案现在的规则，
owner 是 Codex 的任务会永远等下去，而且第 5.3 节的表里没有这一行。

**建议**：`mutedOn` / `canTakeWork == false` 单独成一类「人为停用」，默认动作是
**允许交接且不计入 `handoffCount`**（因为这不是 Agent 的失败）。
同理还有 `runner roles` 里的难度上限、风险等级变更——人改了配置导致 owner 不再合格，
不该被当成故障。

## A.6 逐条回答第十节

**1. 「等原 owner」会不会造成队头阻塞？现有机制能否兜底？**
能兜一半，但有前科。`main.swift:1752` 已经修过队头阻塞（不再只看队头，按队列顺序逐个试，
谁先凑齐候选谁上）。但同一份代码 `main.swift:1965` 记着另一个实锤：
`RepoLease.filter` 预过滤曾把「本轮放行的第一个」记成占坑，而那一个其实派不出去，
结果替 Flint 占了坑、同仓库的动捕步骤每轮「让开」——**队头阻塞修复被租约从背后捅了一刀**。
owner 绑定会制造同一形状的新风险：一个「等 owner」的任务如果仍然占着仓库租约，
同仓库其他任务会被它拖住。**建议**：owner 处于等待态时必须显式释放仓库租约，
并在阶段 1 的测试里直接钉这条（构造「owner 冷却 + 同仓库另一条任务」，断言后者能跑）。

**2. 超时后原 owner 该自动重试几次？怎么区分「任务确实更大」和「Agent 卡死」？**
现有数据帮不上忙（9 条超时全 failed），但**信号已经存在、不用新造**：
worktree 里有没有改动、有没有 WIP commit、日志文件还在不在长大。
「有产出的超时」= 任务更大 → 续一次并放宽时限；「零产出且日志长时间不增长」= 卡死 → 杀掉重开。
建议自动重试上限 1 次，第二次仍超时就转人工，别自动交接。
另外**待修清单第 3 条**（复杂档 45 分钟对 FPS 级编码任务太紧，`c3dcbbaa` 干到 95% 被砍）
说明现在的超时里有相当一部分是**时限设错**，不是 Agent 有问题——
这条应该和阶段 1 一起改，否则 owner 绑定只会让同一个 Agent 反复撞同一堵墙。

**3. `ownerRunnerID` 稳不稳？Runner 改名怎么办？**
**会改名，今晚就改过**：GLM 的干活人从「Claude Code」改叫「ZCode · GLM」（提交 `d931d6a`）。
所以**绝不能用展示名当 key**。`Platform.rawValue` 是稳定的（进过任务库和共享目录 JSON，
改它要迁移全量数据，实际上已经冻结）。建议 `runnerID` 定义成代码里的常量字符串
（如 `minimax.media` / `minimax.review`），与展示名彻底解耦，并在解码时对未知值退回
「按 platform 恢复」而不是判定交接。

**4. Qwen 的 `projectLatest` 和 Claude/ZCode 的 `stableID` 该不该共用一个枚举？**
**不该，你的拆分是对的，而且差异比提案写的更危险**。实测：
Claude 用 `--session-id <id>` / `--resume <id>`，ZCode 用 `--resume <id>`——都是**显式 id**；
Qwen 是 `args.insert("-c", at: 0)`——**没有 id**，语义是「继续这个工作目录里最后一次会话」。
一旦进入阶段 4（每机 2 个执行槽），两条任务在同一 worktree 先后跑 Qwen，
第二条的 `-c` 会接到第一条的会话上，**而且没有任何东西能检测到接错了**。
建议：`projectLatest` 明确标注「与并发不兼容」，阶段 4 的前置条件里写死
「projectLatest 类 Runner 在并发模式下降级为 fresh」。

**5. 普通任务和任务图用不同 session key，统一 owner 后会不会串会话？**
见 A.4——**串会话的风险现在就有**（普通任务 key 是仓库级，不含任务 id）。
统一 owner 不会新增这个风险，但会把它固化。建议连同会话粒度一起定。

**6. 高危任务由指挥兼任，owner 绑定会不会占住控制面？**
会，而且这条要认真对待。当前 `roles.json` 里**只有 Codex 被静音，Claude 没有**，
高危任务仍会落到 Claude（指挥）。一条高危任务绑定 owner = Claude 之后，
如果它长时间等待（额度、冷却），控制面就被一条业务任务占住了。
建议：**高危/控制面任务不参与 owner 绑定**，或给控制面单独一个执行槽——
这比给它设「人工确认」更直接，因为问题不是要不要确认，是槽位被占。

**7. 哪些失败能可靠判成「永久不可用」？**
**建议：任何单一信号都不足以判永久。**两条实锤都会被误判：
① `Proc.run` 每次漏 2 个 fd，常驻 66 分钟漏 2555 个，fd 表满之后**所有**子进程
「退出码 0、输出空」（提交 `937ff52`）——看起来像「这个 CLI 坏了」，其实是本机资源耗尽；
② 磁盘剩 165MB 时全线静默失败（待修清单第 7 条），同样会被记成 Agent 失败。
判永久之前必须让 `work probe` 独立复验一次该平台（探针是单独进程、独立发一句最短的话），
探针也说不行，才允许交接。**一次误分类的代价是全库重读一遍仓库**，值得多花 8 秒。

**8. 阶段 1 能不能不引入新状态枚举？**
能。四个 owner 字段全是可选新增，`decodeIfPresent` 兜底，
旧任务按「尚未分配负责人」处理即可，不需要新 `state`。这一点提案自己的方案已经成立。

## A.7 一个必须老板拍板的业务前提冲突

第十一节写：

> 这套系统优化的目标不是「把所有订阅的进度条都烧完」

**这与老板反复说过的一个目标直接冲突**。他有快到期的订阅套餐，明确要求把额度用掉——
待修清单第 5 条「opencode/火山永不优先」之所以被列为**老板要烧到期套餐的直接障碍**，
就是这个原因。owner 绑定会进一步减少平台轮换，额度会更集中在少数几家，
到期套餐更烧不掉。

技术上我同意提案（上下文连续性优先）；但「烧不烧到期额度」是**商业取舍，不是技术判断**，
不能由设计文档默认掉。**建议把它变成一个显式开关**，而不是一条隐含原则：
比如「新任务首次选人时，对临期套餐给一个可配置的加分」——
这样既不影响已开工任务的 owner 连续性（提案的核心主张不受损），
又能让老板决定烧不烧、烧多少。**这条请老板拍板，不要由 Claude 或 Codex 替他定。**
