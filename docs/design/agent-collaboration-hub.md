# Agent 协作枢纽：MCP-first，A2A-ready

状态：阶段 1 已实现（2026-08-25）

## 目标

同一个 Agent 继续使用自己的原生项目会话，保住隐式上下文和工作习惯；不同
Agent、不同进程和不同机器之间，只交换明确的问题、决定、发现、检查点、证据、
结果和交接。系统不复制隐藏推理，也不把每次接力都伪装成“共享同一个会话”。

最终收益不是让 Agent 多聊天，而是让下一棒少做三件浪费额度的事：重新认识项目、
重复验证已经确认的事实、做完以后才发现前一棒有一个没传过来的关键约束。

## 已实现架构

```text
原生项目会话（每个 Runner 独立）
          │
          ├─ 任务开始时读取相关协作事实并注入增量上下文
          │
          └─ MCP / llmq CLI 写入显式事实
                         │
          collaboration/<machineID>.jsonl
                         │
          现有 iCloud 镜像：只推自己的、只拉别人的
                         │
       另一台机器 / 另一位 Agent / 手机通用页面
```

核心取舍是“每机一份追加日志”，而不是全机器共写一个 mutable JSON。后者会让
最后写入的机器覆盖另一台机器刚留下的消息；追加日志则只需要按事件 ID 去重，
不需要分布式锁或新的数据库。

### 事件契约

`CollaborationEvent` 当前支持：

- `started`：一次真实执行已经开始；
- `question` / `answer`：带 `replyTo` 的可追踪问答；
- `decision` / `finding`：会影响后续工作的决定和发现；
- `checkpoint`：阶段进度和可复查材料；
- `handoff`：失败原因、半成品分支、WIP 提交和已改文件；
- `result`：终态、分支、提交和输出摘要；
- `ack`：幂等确认，说明接收方已纳入后续工作。

事件含项目、任务、任务图、能力泳道、发送/接收 Runner、机器、分支、提交和材料
引用。共享结构采用手写向后兼容解码，旧机器缺字段时不会丢掉整条事件。

### 两条接入路径

1. 支持 MCP 的执行器可以使用 `llmq collaboration mcp`（stdio，无新端口）调用
   `collaboration_get_context`、`collaboration_publish` 和 `collaboration_ack`。
2. 尚未配置 MCP 的执行器仍会在任务提示词里收到相关的增量协作账和一条
   `llmq collaboration publish ...` 命令。编排器还会自动记录开始、提问、交接和终态，
   所以某个 Agent 忘了主动上报也不会让整条执行轨迹消失。

这比强行依赖某个厂商的 MCP 支持稳：协议能力可逐步启用，基本协作不受阻。

### 范围与隔离

- 只读取相同项目；
- 只带相同任务、相同任务图或项目广播；
- 只带广播、明确发给当前 Runner、或当前 Runner 自己发起的线程；
- 默认最多 18 条，避免历史越长提示词越慢；
- 坏 JSON 行跳过，单行损坏不拖垮整本账；
- publish 和 ack 都幂等；summary/details/artifacts 有大小上限；
- MCP 只走标准输入输出，不新增监听端口，不提供网络 shell/exec。

## 手机端

服务端新增动态页面 `collaboration` 和动态菜单入口“Agent 协作”。已有手机通用
渲染器可直接展示最近 30 条协作事实和页面内待回应数，无需因为新增页面重新发版。
页面只读，目的是让人看见 Agent 之间实际发生了什么；Agent 内部确认不混进人的
审批队列，菜单也不挂未读角标，避免重新制造“有一个未读但点进去无事可做”。

## A2A 的位置

现在不直接开放 A2A 网络端点。原因不是否定 A2A，而是当前 Kimi、Claude、Qwen
等 CLI 并没有一个共同且已验证的 A2A 服务能力；先建网络外壳不能解决数据落盘、
跨机冲突、会话亲和和手机可见性。

事件模型已经把发送者、接收者、任务、上下文引用、artifact、reply/ack 独立出来。
将来某个执行器真实支持 A2A 时，只需把 A2A task/message/artifact 映射到这些事件，
无需重写底层存储和移动端。A2A 是适配器，不是第二套真相源。

## 验收标准

- 两台机器同时发布不会互相覆盖；
- 相同事件或确认重试不会产生两个逻辑事件；
- 私有消息不会进入无关项目、任务或 Runner 的上下文；
- 问题收到 answer/ack 后不再显示待回应；
- MCP 工具和 CLI 读写同一份事实；
- 任务开始、提问、失败交接和终态自动留账；
- 手机动态页面能显示协作记录和准确待回应数；
- 镜像、协议和关键过滤有单测，并经过反向变异验证；
- 全量构建和测试通过后，两台机器安装同一发布 SHA。

## 下一阶段（有真实使用数据后再做）

1. 根据真实事件量增加按项目/时间归档，避免 JSONL 无限增长；
2. 从实际 MCP 调用成功率判断哪些 Runner 值得自动生成本地 MCP 配置；
3. 只在至少一个对端实现可互操作 A2A 后增加适配器和契约测试；
4. 用“重复排查减少量、接力首个有效提交耗时、未确认事件寿命”评估收益，
   不用消息条数冒充协作质量。
